    Identify:¶

    When new systems are added to a bot, the code must be edited. One common approach to handle adding a new button input to the code is to simply add a new button check and compare. This works and there is not much wrong with this approach, It gets the job done. However, it has some small drawbacks if you use more advanced types of input. The main drawback is that it makes your code very messy. This makes it hard to find problems or make changes quickly. It also makes harder for anyone else to understand what your code does. Another drawback is that it is repetitive. Code for a new button is often very similar to one of the other buttons; the only difference is usually just checking from a different button. Make your code DRY, not WET. This is one of the greatest principles that all programmers should strive for. DRY code is code in which you D - Don't R - Repeat Y - Yourself. Opposed to WET code, in which you W - Write E - Everything T - Twice.

    Brainstorm:¶

    To make the code cleaner and drier, we are going to use 2 files separate from main.cpp, buttonState.h and buttonState.cpp. The .h, or header file, will be essentially be a clean "list" of functions and variables to be found in the .cpp, or source file. The source file will have the the actual logic. There are many ways to use these files to accomplish our button related tasks. Some of the ways I can think of are:

    Plain functions:¶

    This would be very simple; every button type would have their own function. Every cycle of the code for every button we would call something like: 

    // call an update function that uses the current and prevous button state
bool a_ouptut = updateToggleHoldButton(previousBtnState, 
controller1.get_analog(pros::E_CONTROLLER_DIGITAL_A)); 

// update the last state for next loop
bool previousBtnState = controller1.get_analog(pros::E_CONTROLLER_DIGITAL_A)
// and possibly other variables nessesary for this calculation.


// or, for another button type:
// almost the same as before, but with a different function. 
bool b_ouptut = updateToggleButton(previousBtnState, 
controller1.get_analog(pros::E_CONTROLLER_DIGITAL_B)); 

bool previousBtnState = controller1.get_analog(pros::E_CONTROLLER_DIGITAL_B)
    Then in our header and source files we would define logic for each of those button types. While this is definitely cleaner than rewriting the same logic over and over again, it is far from as clean as it can get.

    Function selector:¶

    Instead of using different functions, we could instead group all of the logic together into a singular function. We would then use a "button type" variable to identify what parts of the logic are relevant to the button. We additionally could use this Identifier to keep track of the variables needed for the calculation. This would look something like: 

    // in an initialization funtion or in the global scope:
// define a new button
Button intakeButton(ButtonType::TOGGLE_HOLD); // and give it a button type.

// then later, in the loop:

bool isIntakeActive =
    intakeButton.update(controller1.get_analog(pros::E_CONTROLLER_DIGITAL_Y))


// and in the header and source:

// a button types list:
enum class ButtonType {
    HOLD,        
    TOGGLE,       
    TOGGLE_HOLD   
};

// a constructor to interpret what type of button it is 
ButtonState(ButtonType t) : type(t) {}

// and any other variables needed 
    ButtonType type;
    bool curr = false;
    bool prev = false;
    int heldMs = 0;

// then all the calculations in the update function.
bool update(bool input) {
    // logic goes here
}
    This is almost exactly what we did for our last bot, but I feel like I can do a little better.

    Everything in the new file:¶

    This builds on the previous version, with a few changes. The logic for these button types needs to be run every cycle. The last 2 version did that by always running an update function for every button. We can instead create a dedicated update all buttons function. Last 2 versions also used controller1.get_analog(pros::E_CONTROLLER_DIGITAL_A) to update the button; we can move this into the external code as well. We would then add a read button output function.

    Select:¶

    I am going to implement the last idea I explained as it leaves the main code very clean.

    Implement:¶

    To start, I made enum class "ButtonType" that defined the button types. Then I made 2 classes: Input and InputGroup. The InputGroup allows me to manage all of the buttons in a group. This is handy if we ever want to use a second controller or have multiple different button layouts in the same code. It has a constructor InputGroup(pros::Controller &controller) : controller(controller) {} this lets us set what controller to read the button inputs from. It also has void addButton(), void updateAll(), and bool getState().

    Adding a button:¶

    Adding a button takes 3 arguments: the name of the new input, and a list (done with a vector) of one or more buttons to use as the input, and what button type it is. For example: 

    // add a new button with a name, input(s), and a button type.
void InputGroup::addButton(std::string name, 
                           std::vector<pros::controller_digital_e_t> 
                           btns, ButtonType type)

    When the function is called, it passes the list of buttons, the button type, and the controller to the Input constructor, creating a new "Input" object. stores the name and the new object in the unordered map, "buttons", like so: buttons.emplace(name, Input(controller, btns, type));

    Updating the buttons:¶

    Running myInputGroup.updateAll() allows us to update all the inputs defined in the input group. The updateAll() function is simple. All it does is reads through the unordered map and runs the update function for each of them, like so: 

    for (auto &[unused, input] : buttons) { // for each input part of the group,
    input.update();                     // run the update function.
}
    The update function however, is not as simple. It is responsible for preparing the output for any of the 6 button types. It starts by updating the previous and current state variables for the button, like so: 
    prev = curr;  // start by updating the previous state variable by coping
              // the current state variable.
curr = false; // reset the current state variable.
    

for (auto btn : buttons) { // then, for every button listed in the buttons vector:
    if (controller.get_digital(btn)) { // check if the button is pressed;
        curr = true; // if it is, set the current state variable to true
        break;       // and stop checking buttons.
    }
}
// if none of the buttons in the vector were pressed;
// the current state variable never changed from when we set it to false.
    After determining the previous and current state of the buttons, It does more logic to determine other variables like rising edge or falling edge detection. This part is much more complicated, so I won't describe it in as much detail.

    First is the "if the button is currently pressed" logic:¶
    if (curr) { // -------------- button is currently pressed -------------- //
    fallingEdge = false; // falling edge is never true if it is pressed
    if (!prev) { // - IS currently pressed and WASN'T prevously pressed - //
        risingEdge = true; // this is the only time rising edge is true
        heldMs = 0; // reset the held time as the button was just pressed
        toggleState = !toggleState; // toggle here so that holding the
                                    // button doesn't repetitively toggle
    } else { // ---- IS currently pressed and WAS prevously pressed ---- //
        risingEdge = false; // no rising edge if it was held previously
        heldMs += LOOP_MS;  // to track held time, add the loop time
    }
    Inside of the "if button is currently pressed" logic, there is also more logic to handle the most complex button type I have defined, specifically the toggle or hold button type:¶

    // ------------- if our button is a toggle hold button ------------- //
if (buttonType == ButtonType::TOGGLE_HOLD &&
    heldMs >= toggleThresholdMs) {  // and it has been held long enough:
    if (InvertedTH) {               // if inverted toggling is on,
        toggleState = !toggleState; // invert the toggle from before
    } else {                        // if inverted toggling is off,
        toggleState = false;        // always cancel toggle state
    }
}
    Having inverted toggling off means that if the state is toggled on and then we hold and release the button, it will turn off. This is fairly intuitive, but sometimes it is useful to have inverted toggling. If the toggled state is on, and then we hold and release the button, instead of resetting it to false, it will set it back to what it was before. For example, We could have a motor that spins when the input state is active. Then we press and release the button before the hold threshold, it toggles on, making the motor spin. if we then press and release the button before the threshold, it will immediately turn off, regardless of whether inverted toggling is on or not. However, if inverted toggling was on and we pressed the button then released it after the threshold, it would turn the motor back on after releasing the button.

    After that is the "if button is not currently pressed" logic:¶

    } else { // -------------- button is NOT currently pressed -------------- //
    risingEdge = false; // rising edge is never true if it is not pressed
    heldMs = 0;         // the button is not held, so the held time is 0
    if (prev) { // - ISN'T currently pressed and WAS previously pressed - //
        fallingEdge = true; // this is the only time falling edge is true
    } else { // - ISN'T currently pressed and WASN'T prevoiusly pressed - //
        fallingEdge = false; // no falling edge if it wasn't held previously
    }
}
    And that is all the logic for the 6 different types of buttons.

    Reading a button:¶

    To read a button, we can run myInputGroup.getState("myInputsName"). The getState() function then looks through the unordered map from before for matching names, in this case, it is looking for "myInputName". It then looks at the object paired with that name, and runs the getOutput() function. The getOutput() function is very simple, it just returns a boolean based on which button type the input is: 

    bool Input::getOutput() {
    switch (buttonType) {           // check what buttonType this input is
    case ButtonType::TOGGLE:        // if it is a toggle button,
        return toggleState;         // return the toggle state
    case ButtonType::HOLD:          // if it is a hold button,
        return curr;                // simply return the current state
    case ButtonType::TOGGLE_HOLD:   // if it is a toggle/hold button,
        return toggleState || curr; // return true if toggle or curr are true
    case ButtonType::RISING_EDGE:   // if it is a rising edge button,
        return risingEdge;          // return the rising edge state
    case ButtonType::FALLING_EDGE:  // if it is a falling edge button,
        return fallingEdge;         // return the falling edge state
    case ButtonType::RISING_FALLING_EDGE: // if it is a rising/falling edge,
        return risingEdge || fallingEdge; // return true if either are true
    default:                              // if it is SOMEHOW not a valid type,
        return curr;                      // return the raw state.
    }
}

    Additionally, the getState() function can take one more argument; a boolean that dictates whether the return should be the raw data or should follow the button type structure. By default the raw flag is set to false, but if we instead set it to one, it simply returns the curr variable: 

    bool InputGroup::getState(std::string name, bool raw) {
    if (!raw) { // check to see if we want the output to be raw or "normal"
        return buttons.at(name).getOutput(); // if normal, use the funtion.
    } else {                          // if the output should be raw,
        return buttons.at(name).curr; // instead return just the curr variable.
    }
}
